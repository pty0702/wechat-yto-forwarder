# 微信 ⇄ 圆通客户管家 消息转发（Python 版）

## 功能与业务规则

以下业务规则已有实现和自动化测试；首次真实双端准备检查已通过，实际发送和 @ 尚未验收，详见“本机兼容性结论”。

微信只处理以 `YT` 加 10～15 位数字开头的文本，允许前导空白。处理顺序为：

| 条件 | 行为 |
|---|---|
| 本账号发送、图片/语音/文件等非文本、非运单消息 | 忽略 |
| 命中屏蔽词 | 忽略 |
| 命中 @客服关键词 | 在微信群选择配置的客服成员并提及，附上原话 |
| 其他合法运单消息 | 原文发送到客户管家目标群，并记录待回复运单 |

客户管家只读取**完整名称与配置一致**的机器人回复，默认 `小圆-总公司`。人工消息、卡片摘要及非文本不搬。机器人回复带单号时，匹配当前等待的该单；不带单号时，沿用最早等待项规则。每条回复发送成功后刷新静默计时，默认 30 秒没有后续回复即结束等待。

**无单号关联是一种启发式规则。** 机器人也回复其他人时，无法仅凭昵称和文本证明消息由本工具触发；多人同时查询、重复查询同一单号或延迟回复都可能出现歧义。需要可靠业务关联时，应使用带请求编号的服务接口。

## 安装与运行

环境：Windows、Python 3.9+（含 Tkinter）、PowerShell 7。以下命令从仓库根目录执行：

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r .\python版\requirements.txt
.\.venv\Scripts\python.exe -X utf8 .\python版\gui.py
```

演示和业务测试只用标准库；真实模式使用 `uiautomation==2.0.29`、`comtypes==1.4.17`。项目创建的虚拟环境保存在工作区内。

实验性微信兼容另外要求 64 位 Windows 和 64 位 Python。新配置中的 `wechat_accessibility` 默认为 `false`；界面复选框“微信4兼容（实验性，停止后恢复）”默认不勾选，演示模式不使用它。

启动界面默认演示模式。演示采用独立样例群、客服、关键词和消息，约十二秒展示筛选、转发、提及、回传和超时，之后继续等待，点击“停止”结束。真实模式使用当前表单的配置；点击“保存配置”才会写入本地文件。

配置损坏会明确报错并保留原文件，禁止覆盖和真实启动；修复后点“重新读取”。任务期间配置暂时锁定，停止完成后可修改。运行、诊断和适配检查均可请求“停止”；关闭窗口也会先通知后台线程停止，等待当前操作及兼容状态恢复完成后退出。适配检查会等待正在进行的准备与恢复步骤结束，不会强制中断界面操作。

## 本机兼容性结论（2026-10-23）

- 微信 `4.1.15.56` 的本机固定构建：临时激活后可读取目标群标题、`chat_input_field` 和 `chat_message_list`；诊断或准备检查结束后恢复原状态 `0`。支持范围仅限核对过的构建。
- 微信发送者读取已实测：普通态 `mmui::ChatTextItemView` 没有发送者子节点；临时进入多选后，按完整 RuntimeId 对应行，并严格扣除“一个空格 + 原始完整正文”后缀取得发送者。恢复后再次核对完整 RuntimeId、正文和顺序，全部一致才接纳。`wechat4` 解析器采用此路径，不根据全宽行位置判断本人。
- 客户管家 `2.0.0.2`／WebView2 `104.0.1293.70`：`yto` 解析器支持数字消息外壳中的 `news-box`、发送者/时间头部和 `text-content` 正文分区，头像不会把纯文本误判为媒体，正文卡片按钮会标为媒体。输入框 `ValuePattern` 不可用，但测试草稿可由 `TextPattern` 完整读回，清除后回到无子节点的单 `U+FFFC` 空叶；实际 UIA 焦点能定位到 `edit-content`，无需放宽焦点判断。发送后本账号气泡可能不显示昵称：此时仅当 `self_names` 只配置了一个完整昵称才判定为本人消息，多个昵称仍拒绝。纯时间/空白行不作为消息，读取时直接跳过。
- 已通过 GUI `Ctrl+T` 完成首次真实双端 `prepare`：两端目标群、草稿读取和消息快照检查通过，微信多选和兼容状态正常恢复。**此次检查没有键入或发送消息；实际发送、发送回显、双向回流和真实 @ 尚未验收。**
- 微信侧已切换为「数据库读 + 坐标/OCR 发」通道（`wechat_db` 解析器）：读消息、发送者与群名走 `vendor/wechatauto` 的本地库接口（SQLCipher 解密微信自身数据文件），发送（含真实 @）走 `WeChatGUI.send_msg / at_member` 并用数据库读回确认落库。不再需要 UIA 多选读发送者，也不再依赖无障碍兼容开关。客户管家发送路径不变。**本通道会读取本机微信自身的聊天数据库（只读，不写库）**；`wechat4` UIA 解析器仍保留可用于不开库的场景。

### 实验性兼容的范围与恢复

兼容选项会临时修改微信进程内已核对的无障碍状态字节。它不修改客户端磁盘文件、不注入代码、不读取聊天数据库。支持范围限定于代码中已审核的构建，进入会话时核对 DLL 的 SHA-256、RVA、指令字节、映像大小和目标页权限；未知构建直接拒绝，不凭相同版本号套用地址，也不保证支持其他微信 4.x。

`accessibility_gate.py` 只做静态 PE 解析，结构匹配本身不能证明候选字段的含义。实际激活由 `WechatAccessibilitySession` 管理：持有原进程句柄，使用进程内登记和 Windows 互斥量避免重叠会话，仅恢复本次会话确实改变的状态。正常结束、点击“停止”和可控异常退出均执行恢复；**强制结束进程、程序崩溃或系统中断不能保证恢复，应重启微信后再使用。** 若恢复失败，日志会明确提示，并要求重启微信和转发工具。

门控特征参考 [WeChatAuto.SDK 的 ForceOpenUITree 实现](https://github.com/scottfly189/WeChatAuto.SDK/blob/c98639483b7d5ef08b87e0c70a65e13c6123213c/WeChatAuto4_X/WeChatAuto/Utils/ForceOpenUITree.cs)，本项目另外执行固定构建及恢复校验。

UIA 的工作前提是应用提供可访问控件，见 [微软 UI Automation Provider 说明](https://learn.microsoft.com/en-us/windows/win32/winauto/uiauto-providersoverview)；接口使用方式见 [uiautomation 项目说明](https://github.com/yinkaisheng/Python-UIAutomation-for-Windows/blob/master/readme_cn.md)。

## 真实窗口对接

1. 登录两边客户端，手动打开对应目标群，保持消息列表在底部，处理完输入框中的草稿。
2. 点击“窗口诊断 (Ctrl+D)”或按 `Ctrl+D`，在日志提示的 5 秒内手动把焦点放回待检查输入框。诊断记录焦点、前台窗口、输入父链、选区端点和文本模式支持信息，不键入或发送。兼容选项未勾选时只读取控件；也可执行不延迟的默认诊断：

   ```powershell
   .\.venv\Scripts\python.exe -X utf8 .\python版\windows_adapter.py --diagnose
   ```

3. 仅在需要测试上述固定构建时，勾选“微信4兼容（实验性，停止后恢复）”再诊断，或明确添加兼容参数：

   ```powershell
   .\.venv\Scripts\python.exe -X utf8 .\python版\windows_adapter.py --diagnose --enable-wechat
   ```

   此路径会临时激活控件。诊断期间可在 GUI 点击“停止”；等待日志确认恢复完成，避免强制结束工具。
4. 根据 `diagnostics/windows-*.json` 中的控件信息，复制 `profiles/uia.example.json` 为 `profiles/local.json` 并填写选择器、本账号在两边的完整群昵称及按键设置。诊断可能包含可见聊天内容，只保存在项目本地，已加入 `.gitignore`。
5. 在界面填写群名、机器人完整昵称和必要关键词，选择适配文件。先按 `Ctrl+T` 或点击“适配检查 (Ctrl+T)”：只创建适配器并执行两端 `prepare`，可能激活微信、右键进入多选再恢复，不键入或发送消息。检查时不要切群或操作客户端。
6. 等待日志显示“检查与恢复已完成”。检查结果保存在本地 `diagnostics/live-check-*.json`。若配置了 @客服关键词，须提供通用 `mention_item`、`mention_token`，或使用下述微信 4 提及模式。
7. 点击“单次发送验收…”或按 `Ctrl+Shift+T`，选择微信或客户管家，查看目标群及固定文本“转发工具联调测试，请忽略。”，确认后才点“发送这一条”。微信端可勾选真实 @ 客服。每次只向选定端发送一条，结束即停止，失败不自动重试。真实转发、回流和 @ 应分别验收，预检通过不能代替发送验收。

启动先核对两边群标题、输入框的完整草稿读取能力和消息快照；找不到控件、出现多个匹配或遇到未被限定空叶规则覆盖的对象占位符时会报错。程序不会自动搜索并切换群聊。适配器固定绑定首次确认的 PID，微信兼容会话与该进程保持同一生命周期；进程变化时拒绝继续收发，即使新进程名称相同也不会自动接管，需要重新启动转发会话。运行期间切群会拒绝相关操作，列表失去快照重叠时会重新建立基线。

### 适配配置格式

顶层包含 `wx`、`kf` 两个对象。每个对象包含：

| 字段 | 含义 |
|---|---|
| `window` | 顶层窗口选择器，建议 `depth: 1` 并填写名称、类名或标识 |
| `process_name` | 可选，核对窗口所属进程的 EXE 文件名；运行中仍固定绑定首次确认的 PID |
| `group_title` | 当前会话标题选择器，最终控件名称必须等于配置群名 |
| `messages` / `message_item` | 消息容器与消息行选择器，必须保持时间顺序 |
| `parser` | `selectors`、客户管家 `yto` 或仅用于 `wx` 的 `wechat4`；未知值拒绝 |
| `sender` / `content` | 通用解析器的发送者与正文选择器；省略正文时使用消息行 Name |
| `self_names` | 本账号在当前群的完整昵称列表，用于排除本人消息和确认发送回显 |
| `input` | 输入区域选择器，必须可读取完整草稿 |
| `id_attribute` | `automation_id` 或 `runtime_id`，用于识别消息事件 |
| `send_keys` / `newline_keys` | 发送、换行快捷键，必须与客户端设置一致且不能相同 |
| `mention_item` / `mention_token` | 微信 @候选与选中后的真实提及标记，使用 `{staff}` 代表客服名 |
| `mention_mode` | `wechat4` 解析器可显式设为 `"wechat4"`，使用本机已核对的提及弹窗和嵌入对象流程 |
| `mention_allow_duplicate_names` | 布尔值，默认 `false`；只有用户允许任意同名成员时才设为 `true`，仍要求昵称完整匹配 |
| `text_pattern_suffix` | 仅供已确认会追加结构性段落符的输入控件使用；不能剥掉用户草稿或 `U+FFFC` 对象占位符 |
| `text_pattern_empty_leaf` | 布尔值，默认 `false`；仅 `parser: "yto"` 且 `process_name: "YtoChatApp.exe"` 可启用，限定规则见下方 |
| `context_points` | `wechat4` 必填的两个不同右键比例点，如 `[[0.25, 0.6], [0.75, 0.6]]`；坐标均严格在 0～1 之间，必须按本机消息布局确认 |
| `menu_depth` | `wechat4` 查找消息菜单的深度，默认 `8`，范围 1～20 |

选择器支持 `name`、`automation_id`、`class_name`、`type` 的完整匹配，以及各字段加 `_regex` 的完整正则匹配。`depth` 为 1～40；`index` 为从 0 开始的可选明确索引，只有结构稳定时才使用。对象数组表示逐层查找。`{group}` 会替换为界面配置的目标群名。

`wechat4` 的 `window` 必须是单个顶层选择器对象。消息容器应定位 `chat_message_list`，适配器只读取其直接子级 `mmui::ChatTextItemView` 文本行；输入框应定位 `chat_input_field`。示例中的右键点仅展示格式，不证明适合其他窗口尺寸或客户端构建。`self_names` 使用本账号在该群的完整昵称，昵称相同仍不能证明账号相同。

客户管家的 `text_pattern_empty_leaf: true` 只把以下状态视为空：完整 `TextPattern` 文本**恰好是单个 `U+FFFC`**，输入控件是 `GroupControl`、AutomationId 为 `edit-content`，并且没有任何子节点。混合或多个占位符、已有子节点、控件身份不符、读取失败均不视为空，也不能用 `text_pattern_suffix` 绕过。代码核对配置和控件条件，不自动核对客户管家版本；只在本机完成空输入、测试草稿完整回读和清除复验后启用。示例默认关闭。

通用提及流程要求 `mention_item` 和 `mention_token`。微信 4 可改用 `mention_mode: "wechat4"`：从同进程的 `MentionPopover` 内选择昵称完整匹配的成员，选中后要求弹窗消失，输入框的 Value/Text 模式均为单个 `U+FFFC`，再添加正文。此占位符只在本次候选点击流程中作为已选中嵌入对象的证据，不能单独证明账号身份；同名默认拒绝，用户明确允许后才选任意同名项。草稿与发送后可读正文分开严格校验，回显不符就停止。本机已人工验证候选与嵌入对象，程序真实提及发送仍待验收。

### 可靠性边界

- 发送确认要求发送前列表非空，原末尾消息锚点在发送后仍存在，匹配的本人完整正文出现在该锚点之后且事件 ID 不在原快照中，同时输入框草稿已清空。控件整体重建或锚点前新显露的同文历史不能充当回显；发送前列表为空直接拒绝，不尝试输入。回显确认窗口为 12 秒，覆盖消息渲染与微信多选往返读取身份的耗时；超时错误只报告计数与结构原因（锚点是否命中、本人新消息数、正文一致数），不记录消息正文。
- 输入框已有任何草稿时不覆盖。无法读取完整草稿或可靠识别本人消息时拒绝继续；已通过准备检查也必须单独验证实际输入和发送结果。
- 明确未发送的失败保留原事件并重试。提交后回显缺失或发生未知发送错误时停止，需要人工核对后重新运行。
- 不按正文永久去重，相同文本的不同事件可以正常处理。客户端控件标识不稳定、被复用或同名用户仍会限制识别可靠性。
- 微信发送阶段重新进入多选核对发送者，不用旧缓存确认本人回显。发现群、消息容器或快照连续性变化时清除发送者缓存；未观察到的往返切群、同 ID 同正文复用及同名用户仍无法仅靠 UIA 排除。RuntimeId 不是服务端消息 ID，运行期间应保持目标会话不变。
- 多选恢复失败后禁用当前适配器实例，保留原操作与恢复错误；后续轮询不会再次操作它。需要人工恢复界面后重新启动会话。
- 第一帧非空快照只作历史基线；完全空白会话的首条消息可能被作为基线忽略。消息列表重载、滚动或轮询间隙大量消息使旧锚点消失时，优先重新建基线，可能漏掉这段消息，日志会提示。
- 只轮询可访问的消息行，不能补偿客户端尚未加载的消息。运行期间请勿切群、翻历史或同时在输入框中键入。
- 停止、重启后不恢复内存待办和等待队列；不会自动补发历史。已收到且成功关联、但因发送失败暂存的回复，在当前运行中会继续重试；超时后才新收到的回复丢弃。
- 支持同一运单连续多条回复，但无编号回复的关联仍有前述歧义。
