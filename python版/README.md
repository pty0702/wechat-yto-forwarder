# 微信 ⇄ 圆通客户管家 消息转发（Python 版）

## 功能与业务规则

以下业务规则已有实现和自动化测试；真实窗口收发尚未完成验收，当前阻碍见“本机兼容性结论”。

微信只处理以 `YT` 加 10～15 位数字开头的文本，允许前导空白。处理顺序为：

| 条件 | 行为 |
|---|---|
| 本账号发送、图片/语音/文件等非文本、非运单消息 | 忽略 |
| 命中屏蔽词 | 忽略 |
| 命中 @客服关键词 | 在微信群选择配置的客服成员并提及，附上原话 |
| 其他合法运单消息 | 原文发送到客户管家目标群，并记录待回复运单 |

客户管家只读取**完整名称与配置一致**的机器人回复，默认 `小圆-总公司`。人工消息、卡片摘要及非文本不搬。机器人回复带单号时，匹配当前等待的该单；不带单号时，沿用最早等待项规则。每条回复发送成功后刷新静默计时，默认 30 秒没有后续回复即结束等待。

**无单号关联是一种启发式规则。** 机器人也回复其他人时，无法仅凭昵称和文本证明消息由本工具触发；多人同时查询、重复查询同一单号或延迟回复都可能出现歧义。需要可靠业务关联时，应使用带请求编号的服务接口。

## 文件

| 文件 | 用途 |
|---|---|
| `gui.py` | 中文配置窗口、演示/真实模式、运行控制、日志、窗口诊断、实验性兼容开关 |
| `runtime.py` | 会话装配和分阶段演示 |
| `wechat_forwarder.py` | 规则、队列、事件去重、重试和可停止主循环 |
| `windows_adapter.py` | UI Automation 选择器、消息解析、真实收发、诊断 |
| `message_snapshot.py` | 跳过启动历史，识别新增消息事件 |
| `accessibility_gate.py` | 只读解析磁盘 PE 文件，定位并核对无障碍门控的结构候选 |
| `wechat_accessibility.py` | 对已核对的固定构建临时激活无障碍状态，管理互斥会话与恢复 |
| `profiles/uia.example.json` | 适配配置格式示例，需要按实际客户端调整 |
| `config.json` | 用户本地配置，界面保存生成，不提交 |
| `tests/` | 业务、模拟窗口、PE 校验与兼容会话恢复测试 |

## 安装与运行

环境：Windows、Python 3.9+（含 Tkinter）、PowerShell 7。以下命令从仓库根目录执行：

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r .\python版\requirements.txt
.\.venv\Scripts\python.exe -X utf8 .\python版\gui.py
```

演示和业务测试只用标准库；真实模式使用 `uiautomation==2.0.29`、`comtypes==1.4.17`。项目创建的虚拟环境保存在工作区内。

实验性微信兼容另外要求 64 位 Windows 和 64 位 Python。新配置中的 `wechat_accessibility` 默认为 `false`；界面复选框“微信4兼容（实验性，停止后恢复）”默认不勾选，演示模式不使用它。

启动界面默认演示模式。演示采用独立样例群、客服、关键词和消息，约十二秒展示筛选、转发、提及、回传和超时，之后继续等待，点击“停止”结束。真实模式使用当前表单的配置；点击“保存配置”才会写入本地文件。

配置损坏会明确报错并保留原文件，禁止覆盖和真实启动；修复后点“重新读取”。任务期间配置暂时锁定，停止完成后可修改。运行和窗口诊断均可点击“停止”；关闭窗口也会先通知后台线程停止，等待当前操作及兼容状态恢复完成后退出。

## 本机兼容性结论（2026-10-23）

- 微信 `4.1.15.56` 的本机固定构建：未启用兼容时只暴露窗口和窗格；已通过 GUI 的“窗口诊断”临时激活无障碍状态，读取到目标群标题、`chat_input_field` 和 `chat_message_list`，诊断完成后正常恢复原状态 `0`。**控件激活与恢复已验证，真实双向收发及真实 @ 尚未验收。**
- 微信消息解析仍有缺口：`mmui::ChatTextItemView` 是全宽消息行，没有发送者子节点，已检查的 Help/Legacy 属性为空。不能把它当作已有 sender 子控件的 `selectors` 结构，也不能据全宽行的左右位置判定是否本人发送。本人过滤及回传自环防护未获可靠依据前，不应启用自动搬运。
- 客户管家 `2.0.0.2`：可读取 `FrmMainView`、`imLayout`、数字消息标识、发送者文本及正文组；`yto` 解析器依据这一结构编写。但 `edit-content` 的 `ValuePattern` 不可用，`TextPattern` 返回 `U+FFFC` 对象占位符，尚不能确认读到了完整草稿。启动时的 `prepare` 检查会明确拒绝该状态，不能通过 `text_pattern_suffix` 剥掉占位符绕过。输入、发送及发送回显仍待验收。
- 本次未向真实群发送验收消息。132 项自动化测试通过，包含业务规则、模拟控件和兼容恢复路径；测试通过不等于真实客户端端到端收发通过。

### 实验性兼容的范围与恢复

兼容选项会临时修改微信进程内已核对的无障碍状态字节。它不修改客户端磁盘文件、不注入代码、不读取聊天数据库。支持范围限定于代码中已审核的构建，进入会话时核对 DLL 的 SHA-256、RVA、指令字节、映像大小和目标页权限；未知构建直接拒绝，不凭相同版本号套用地址，也不保证支持其他微信 4.x。

`accessibility_gate.py` 只做静态 PE 解析，结构匹配本身不能证明候选字段的含义。实际激活由 `WechatAccessibilitySession` 管理：持有原进程句柄，使用进程内登记和 Windows 互斥量避免重叠会话，仅恢复本次会话确实改变的状态。正常结束、点击“停止”和可控异常退出均执行恢复；**强制结束进程、程序崩溃或系统中断不能保证恢复，应重启微信后再使用。** 若恢复失败，日志会明确提示，并要求重启微信和转发工具。

门控特征参考 [WeChatAuto.SDK 的 ForceOpenUITree 实现](https://github.com/scottfly189/WeChatAuto.SDK/blob/c98639483b7d5ef08b87e0c70a65e13c6123213c/WeChatAuto4_X/WeChatAuto/Utils/ForceOpenUITree.cs)，本项目另外执行固定构建及恢复校验。

UIA 的工作前提是应用提供可访问控件，见 [微软 UI Automation Provider 说明](https://learn.microsoft.com/en-us/windows/win32/winauto/uiauto-providersoverview)；接口使用方式见 [uiautomation 项目说明](https://github.com/yinkaisheng/Python-UIAutomation-for-Windows/blob/master/readme_cn.md)。

## 真实窗口对接

1. 登录两边客户端，手动打开对应目标群，保持消息列表在底部，处理完输入框中的草稿。
2. 点击“窗口诊断 (Ctrl+D)”或按 `Ctrl+D`。兼容选项未勾选时只读取控件；也可执行默认诊断：

   ```powershell
   .\.venv\Scripts\python.exe -X utf8 .\python版\windows_adapter.py --diagnose
   ```

3. 仅在需要测试上述固定构建时，勾选“微信4兼容（实验性，停止后恢复）”再诊断，或明确添加兼容参数：

   ```powershell
   .\.venv\Scripts\python.exe -X utf8 .\python版\windows_adapter.py --diagnose --enable-wechat
   ```

   此路径会临时激活控件。诊断期间可在 GUI 点击“停止”；等待日志确认恢复完成，避免强制结束工具。
4. 根据 `diagnostics/windows-*.json` 中的控件信息，复制 `profiles/uia.example.json` 为 `profiles/local.json` 并填写选择器、本账号在两边的完整群昵称及按键设置。诊断可能包含可见聊天内容，只保存在项目本地，已加入 `.gitignore`。
5. 在界面填写群名、机器人完整昵称、客服昵称和关键词，选择适配文件。**当前微信发送者与客户管家草稿读取尚未解决，不能只填入选择器就认定适配完成。** 完成解析、输入和真实 @ 的必要验证后，才可进入真实收发验收。

启动先核对两边群标题、输入框的完整草稿读取能力和消息快照；找不到控件、出现多个匹配或草稿读取返回对象占位符时会报错。程序不会自动搜索并切换群聊。适配器固定绑定首次确认的 PID，微信兼容会话与该进程保持同一生命周期；进程变化时拒绝继续收发，即使新进程名称相同也不会自动接管，需要重新启动转发会话。运行期间切群会暂停相关操作，列表失去快照重叠时会重新建立基线。

### 适配配置格式

顶层包含 `wx`、`kf` 两个对象。每个对象包含：

| 字段 | 含义 |
|---|---|
| `window` | 顶层窗口选择器，建议 `depth: 1` 并填写名称、类名或标识 |
| `process_name` | 可选，核对窗口所属进程的 EXE 文件名；运行中仍固定绑定首次确认的 PID |
| `group_title` | 当前会话标题选择器，最终控件名称必须等于配置群名 |
| `messages` / `message_item` | 消息容器与消息行选择器，必须保持时间顺序 |
| `parser` | `selectors` 或已实现的客户管家 `yto` 解析器 |
| `sender` / `content` | 通用解析器的发送者与正文选择器；省略正文时使用消息行 Name |
| `self_names` | 本账号在当前群的完整昵称列表，用于排除本人消息和确认发送回显 |
| `input` | 输入区域选择器，必须可读取完整草稿 |
| `id_attribute` | `automation_id` 或 `runtime_id`，用于识别消息事件 |
| `send_keys` / `newline_keys` | 发送、换行快捷键，必须与客户端设置一致且不能相同 |
| `mention_item` / `mention_token` | 微信 @候选与选中后的真实提及标记，使用 `{staff}` 代表客服名 |
| `text_pattern_suffix` | 仅供已确认会追加结构性段落符的输入控件使用；不能剥掉用户草稿或 `U+FFFC` 对象占位符 |

选择器支持 `name`、`automation_id`、`class_name`、`type` 的完整匹配，以及各字段加 `_regex` 的完整正则匹配。`depth` 为 1～40；`index` 为从 0 开始的可选明确索引，只有结构稳定时才使用。对象数组表示逐层查找。`{group}` 会替换为界面配置的目标群名。

配置 @关键词时，当前适配器必须同时提供 `mention_item` 和 `mention_token`。程序会输入客服名称、选择唯一候选并核对真实提及标记，缺少支持时拒绝把普通 `@名字` 文本当作已完成提及。本机微信的候选交互和选中后标记尚未验收，不能随意填写选择器绕过检查。

### 可靠性边界

- 发送确认要求发送前列表非空，原末尾消息锚点在发送后仍存在，匹配的本人完整正文出现在该锚点之后且事件 ID 不在原快照中，同时输入框草稿已清空。控件整体重建或锚点前新显露的同文历史不能充当回显；发送前列表为空直接拒绝，不尝试输入。
- 输入框已有任何草稿时不覆盖。无法读取完整草稿或可靠识别本人消息时，不能通过发送验收；本机当前仍存在这些缺口。
- 明确未发送的失败保留原事件并重试。提交后回显缺失或发生未知发送错误时停止，需要人工核对后重新运行。
- 不按正文永久去重，相同文本的不同事件可以正常处理。客户端控件标识不稳定、被复用或同名用户仍会限制识别可靠性。
- 第一帧非空快照只作历史基线；完全空白会话的首条消息可能被作为基线忽略。消息列表重载、滚动或轮询间隙大量消息使旧锚点消失时，优先重新建基线，可能漏掉这段消息，日志会提示。
- 只轮询可访问的消息行，不能补偿客户端尚未加载的消息。运行期间请勿切群、翻历史或同时在输入框中键入。
- 停止、重启后不恢复内存待办和等待队列；不会自动补发历史。已收到且成功关联、但因发送失败暂存的回复，在当前运行中会继续重试；超时后才新收到的回复丢弃。
- 支持同一运单连续多条回复，但无编号回复的关联仍有前述歧义。
